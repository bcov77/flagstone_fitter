# Flagstone patio geometry (Phase 1)

Start with [the project layout and collaborator guide](PROJECT_LAYOUT.md) for
the current packing/physics pipeline, setup, and multi-day production command.
This repository tracks selected source and documentation; private stone inputs
and historical results are not included. The sections below describe the
project's development and earlier tools.

For the 25-foot synthetic patio, `sampled_voids(layout, spacing=1/24,
diameter=1/3)` estimates the largest empty circle and the area of grid cells
whose centers allow a four-inch circle, counting patio boundaries and stones as
obstacles. These are sampled diagnostics, not a guarantee or a count of holes.
`uv run python scripts/repair_large_gaps.py --input path/to/layout.json --output
examples/my_repair --seconds 30` tries unused small stones near the largest
sampled gap, preserves existing poses, and saves fully validated improvements.
Input must use feet and the script uses a half-inch minimum pair and edge gap;
the output directory must not already contain a repair result. An example and
before/after image are in `examples/gap_repair`. This direct-insertion pass does
not rearrange stones or guarantee a four-inch maximum hole.

For PackingSolver, `scripts/long_packingsolver.py` accepts optional
`--void-diameter` and `--void-spacing` (both in layout units) to save the best
validated gap-core candidate separately from the best-coverage candidate. It
scores only candidates that the solver emits, and these sampled scores are not
a native PackingSolver objective. Sampling adds work and affects throughput.

Python 3.12+, managed with uv. Setup: `uv sync`; run `uv run python -m flagstone`.
Synthetic examples use normalized units (the square patio is 1 × 1). Schema version 1 also accepts `m`, `cm`, `mm`, `ft`, and `in`; coordinates, gap, edge clearance, and tolerance must use the same units, with no automatic conversion. The example CLI uses 0.01 as a synthetic default only for generated examples; imported layouts require explicit clearances, and checkpoint resumes use the saved values. Physical clearance and numerical tolerance are separate. Pair validation checks direct distance with a default 1e-9 slack and rejects physical overlap. Boundary validation requires both inset coverage and direct distance to the physical boundary; the inset is strict, so it may reject a borderline case even when distance lies within tolerance. Buffer arcs are approximate.

Phase 1 geometry helpers are in `src/flagstone/phase1.py`. Schema version 1 JSON includes patio outline, stable IDs, local outlines, poses and active flags. Local shapes are centered at area centroid; poses store centroid location and radians. On import, the original outline is retained as `source_outline`, and its centroid provides the translation from source coordinates to local coordinates; the pose is adjusted to preserve its world placement. Only finite 2D simple rings without holes are supported.

Run `uv run python -m flagstone --case witness --output examples/witness` for a cut-and-shrink witness, or `uv run python -m flagstone --case search --output examples/search` for a seeded greedy insertion baseline. Each writes a plot, layout, metrics, and atomic checkpoint. Resume the remaining inventory with `--resume examples/search/checkpoint.json --output examples/resumed`; the saved random state is restored. This baseline only tries random positions and rotations; it does not yet implement the full search or complete checkpoint schedule described in the plan. Use `uv run pytest -q` for the current checks.

`flagstone.diagnostics.empty_space(layout, resolution=100)` estimates distances from sampled empty patio points to the nearest stone. It records grid resolution and can separate an `edge_strip_width` from the interior and estimate sampled area beyond a `broad_distance` threshold. It does not certify clearance or measure joint width. Relaxation accepts optional per-stone `mobility` and `tethers`, a reference pose array, and a 2-D directional `pressure`; its normalized area penalty is a local guide and final validity is always checked separately. A valid input without pressure is returned unchanged. The algorithm is a slow coordinate-descent reference and can stall on deep overlaps.

Use `--strategy mixed`, `corner`, `boundary`, or `opening` to alternate the corresponding grid-based proposals with random positions; the grid only proposes candidates and the polygon validator decides acceptance. `greedy_insert(..., relaxation_steps=N)` optionally relaxes a bounding-circle neighborhood around each proposal. `uv run python scripts/relaxation_demo.py` generates the controlled narrow-slot rotation before/after plots in `examples/relaxation`.

Add `--rebuild-rounds 10 --patch-size 2` to try local removal and reinsertion after the initial search. A patch is accepted only if its fully validated coverage increases; rejected patches restore all poses and active flags while the random generator advances. `uv run python scripts/benchmark_search.py --seconds 1 --seeds 3` compares random and mixed proposals over equal nominal wall-clock budgets and saves per-run data to `examples/benchmark.json`. Budgets are checked between proposals, so individual operations and final validation can cause small overruns; timing results vary by machine. This short experiment is not a production performance claim.

For a rebuild that can survive interruption, run `uv run python -m flagstone --case search --durable-rebuild --rebuild-rounds 20 --output examples/durable`. Resume with `uv run python -m flagstone --resume examples/durable/rebuild_checkpoint.json --rebuild-rounds 40 --output examples/resumed`; the round count is the total target, and saved settings and RNG state are used. Each completed rebuild round is written atomically. An interruption during a round replays that round from the previous checkpoint; initial insertion is checkpointed when `--durable-insertion` is enabled. The current valid state is also the incumbent because this runner only accepts improvements.

CLI metrics include physical placed area, coverage, counts and minimum measured pair/edge distance. If any stone lies outside the patio, edge distance is undefined and the offending IDs are reported. Physical distance diagnostics do not replace validation.

Add `--durable-insertion` to checkpoint the initial greedy insertion at each stone boundary in `insertion_checkpoint.json`. Resume an interrupted insertion with `--resume path/to/insertion_checkpoint.json`; saved proposal settings and RNG state govern the resumed insertion. Work within the interrupted stone is retried. The insertion and rebuild checkpoints are separate: after resuming an insertion, pass `--durable-rebuild --rebuild-rounds N` to begin a durable rebuild.

`relax_with_restarts` optionally applies bounded, seeded translation and angle perturbations after failed downhill relaxation, respecting zero-mobility stones and retaining the best candidate. Run `uv run python scripts/benchmark_relaxation.py` for a controlled deep-containment case, and `uv run python scripts/profile_reference.py` for single-run CPU timings at 25–200 active stones. These are diagnostic experiments, not representative construction performance or evidence of GPU speedup.

`flagstone.batch.relax_batch` provides a serial CPU reference interface for independent `[batch, stones, 3]` pose arrays and per-candidate active masks; it shares immutable geometry but does not accelerate execution. It is intended for validating future backends.

Layout metrics include unused stone area, smallest unused area, and uncovered patio area. Uncovered area uses the union of placed polygons clipped to the patio, while the reported coverage is the sum of stone areas divided by patio area and is meaningful as coverage only for a valid layout.

For explicit deterministic uncertainty bounds, construct `StoneUncertainty(shape=..., translation=..., rotation=...)` per stone and call `stone_margins(layout, bounds_by_id)`. Shape and translation are length bounds in the layout's units; rotation is an absolute angle bound in radians. The resulting outward displacement bound adds shape error, translation error, and `2 * radius * sin(min(rotation, pi) / 2)`, with radius measured from the local pose origin. Supply the result as `stone_margins=...` and a separate patio boundary error as `patio_margin=...` to `validate`, `greedy_insert`, `rebuild_search`, or the durable runner. The pair requirement becomes `gap + margin_i + margin_j`, and the edge requirement becomes `edge + patio_margin + margin_i`. Unspecified stone IDs have zero margin. The search acceptance checks and optional relaxation energy both use these bounds. Relaxation uses approximate polygon buffers, so final direct-distance validation remains authoritative. These are worst-case arithmetic bounds based on values supplied by the user, not measurements or probability estimates. No default values are construction recommendations.

When resuming a checkpoint, the CLI uses its stored gap, edge and uncertainty margins, including when it starts a subsequent rebuild. Clearance outlines in the plot show the nominal pair gap only; they do not show the per-stone uncertainty margins.

Pass `frozen_ids=[...]` to `greedy_insert`, `rebuild_search`, `start_insertion`, or `start_rebuild` to keep already-active stones fixed and prevent their removal. Frozen IDs are saved in durable checkpoints and carried into subsequent CLI rebuilds. The optimizer still requires a valid starting arrangement; it cannot certify that a physical stone has actually been placed at the entered pose.

CLI examples write a validated `placement.json` with patio outline, units, modeled clearances, stone centroids, angles, and corresponding local/world orientation marks. The default order is explicitly inventory order, not a recommended construction sequence. `placement_manifest(..., order=...)` accepts a user-supplied order containing every active stone exactly once. These coordinates are based on the entered geometry and origin; real measurements, placement references, and a build sequence still need to be supplied and checked before field use.

The CPU relaxation caches unchanged stone geometry during each sweep and recomputes moved-stone contacts; the full objective is recomputed after each sweep and final validity is checked independently. Run `uv run python scripts/profile_reference.py --all-mobile --output examples/reference_profile_all_mobile.json` to profile one step with every stone mobile.

To pack a version 1 layout file, provide its clearances in the file's stated units: `uv run python -m flagstone --input examples/physical_input/synthetic_feet.json --gap .10 --edge .15 --strategy opening --output examples/physical_output`. This is a synthetic feet-based demonstration, not measured patio data or a recommendation. The input JSON contains `schema_version`, `units`, a patio ring, and stone records with an `id`, local `outline`, `[x, y, angle_radians]` pose, and boolean `active`. Inactive stones are available inventory; active stones must initially form a valid layout. Use a separate output directory to keep the original input untouched.

For this CLI path, `--freeze ID` keeps an existing active stone fixed, `--patio-margin N` adds a boundary error bound, and `--stone-margins margins.json` supplies a JSON object mapping stone IDs to already-computed length margins. Omitted margins are zero. When resuming, the saved clearances, margins, and frozen IDs are used; change them by starting a new run rather than overriding the checkpoint.

`--explore-rounds N --max-coverage-drop 0.05` starts a checkpointed patch search that may accept a valid exploratory layout up to five percentage points of patio area below the best found. The incumbent is kept separately and is what the CLI exports. Resume with `--resume path/to/exploration_checkpoint.json --explore-rounds TOTAL`; the file retains the exploratory state, best poses and flags, RNG, schedule, and histories. Moves are accepted by a bounded coverage rule, not simulated annealing. `scripts/benchmark_exploration.py` compares this operator with strictly greedy rebuilding under equal nominal post-insertion budgets, including checkpoint I/O.

`sampled_neighbor_distances(layout, spacing=..., max_distance=...)` samples each placed stone's boundary and measures proximity to the nearest other stone, reporting the number of samples excluded by the cutoff. Samples are directed and approximately perimeter-weighted; these distances are a joint-quality proxy, not full joint widths or a clearance test. `uv run python scripts/diagnostic_sensitivity.py` records multiple sampling resolutions for the example layout.

For a synthetic inventory with about 20 vertices per outline, pass `vertex_profile='detailed'` to `inventory`, or `--detailed` to the search benchmark and reference profiler. This generator uses elliptical convex hulls with occasional synthetic notches; it is not a substitute for measured stone outlines.

For outlines traced in **one common source coordinate frame**, `uv run python -m flagstone.calibration examples/calibration/synthetic_measurements.json --max-residual .001 --output examples/calibration/layout.json --report examples/calibration/report.json` fits a uniform-scale 2D rotation and translation using at least three non-collinear paired control points. `reflect_source_y: true` explicitly flips a source image's downward-pointing y axis before fitting. The required residual limit is in target units. The report retains raw rings, control points, fitted transform, and control residuals; the output layout uses calibrated units and preserves each outline's geometry under that single transform. Then run the normal `--input` workflow with explicit gap and edge clearances.

Control-point residuals do not bound perspective, lens distortion, tracing errors, or errors away from the controls. The calibration assumes a common planar frame and one uniform scale; separately photographed stones need independent calibrations before combining. The bundled example is synthetic.

`flagstone.broadphase.PaddedGeometry` and `candidate_pairs` provide a NumPy batch prototype for transforming variable-length outlines and proposing pairs by conservative expanded bounding boxes. It supports per-candidate active masks and per-stone margins. The result is only a broad-phase candidate list: exact CPU polygon distance/intersection checks are still required. It allocates arrays proportional to batch × stones², but does not allocate edge-pair matrices. `uv run python scripts/benchmark_broadphase.py` compares its full filter-plus-exact-contact path with a Shapely spatial tree on the local machine; this prototype is not a GPU backend or an end-to-end solver benchmark.

`flagstone.batch.validate_batch` combines the NumPy broad phase with the same exact CPU polygon distance, intersection and patio checks as scalar validation. It returns per-layout violations without changing the inputs. `uv run python scripts/benchmark_batch_validation.py` measures complete batch validation against independent scalar calls and records Python-traced peak memory; native GEOS memory may be omitted. This remains a CPU prototype, and the single-layout validator remains available as the reference.

An experimental `--strategy random --batch-size 8` evaluates insertion proposals in CPU batches without local relaxation. The first apparently valid proposal is rechecked by the scalar validator before acceptance. Batch size changes the random trajectory because every proposal in a batch consumes random draws. Durable insertion checkpoints retain the batch size. In the short local whole-search comparison saved in `examples/batched_search_benchmark.json`, this mode did not outperform scalar insertion; batching remains optional and is not a GPU backend.

`--relaxation-steps N` enables local relaxation during insertion and rebuilding; `--relaxation-step` sets its translation step in layout units and is required for physical-unit layouts when relaxation or pulses are requested. `--pulse-rounds N` enables a separate bounded move after insertion: `--translation-noise`, `--angle-noise` and optional `--pressure X Y` configure vibration and directional pressure, and `--pulse-steps` bounds recovery work. Each pulse starts from a valid layout and rolls back if exact validation fails; frozen stones stay fixed. These moves rearrange stones but do not themselves increase placed area. Pulse rounds are not individually checkpointed and cannot be inserted into a resumed rebuild/exploration schedule; they are not a physical simulation.

New checkpoints use version 2 with a run ID, UTC save time, software versions, a geometry fingerprint (patio, units, IDs and local outlines), and a SHA-256 digest over the complete stored checkpoint. Loading verifies the digest before reconstructing state. This detects accidental corruption; it is not a signature and cannot authenticate a file against intentional modification. Version 1 checkpoints remain readable without integrity verification. Durable run IDs persist across checkpoint updates; separate phases may start new run IDs.

For independently measured outlines, use `uv run python -m flagstone.calibration examples/calibration/synthetic_bundle.json --bundle --output examples/calibration/bundle_layout.json --report examples/calibration/bundle_report.json`. Each patio/stone record has its own source units, outline, non-collinear control points, optional y reflection, and maximum permitted residual; all target controls use the bundle's target length units. Patio target coordinates define the patio frame. Each stone's target coordinates define its own measurement frame, after which the outline is centered. An active stone requires an explicit patio-frame `[centroid_x, centroid_y, angle_radians]` pose; inactive stones default to `[0, 0, 0]`. The report retains each original ring and independent fit. This is a synthetic example; calibration residuals still do not measure unmodeled distortion or tracing errors.

`--uncertainty-model path.json` accepts a version 1 file with the layout's `units`, an explicit nonnegative `patio` bound, and a `stones` object containing **every** stone ID. Each stone must provide `shape` and `translation` bounds in layout units and a `rotation` bound in radians. See `examples/calibration/synthetic_uncertainty.json` for a synthetic example. The command derives margins, retains the original components in checkpoints and the placement manifest, and verifies consistency when resuming. This option cannot be combined with `--stone-margins` or `--patio-margin`. Values are inputs, not estimated measurements or recommended construction tolerances; numeric zero is an explicit assumption.

`placement_map.png` is a validated planning map with coordinate axes, a data-unit scale bar, stone IDs, and the modeled orientation mark. The mark corresponds to the first vertex in the centered model outline; `placement.json` records that point in local, patio, and (when available) source-outline coordinates, along with model edge lengths and perimeter. The map is not a physical-size print template, and its default ordering is not a placement sequence. Labels may become crowded in dense layouts; use the JSON coordinates and outlines for inspection.

`--strategy contact` alternates random positions with proposals beside a placed stone's rotated bounding box, accounting for nominal gap and per-stone margins before the exact validity check. This is a heuristic: it does not guarantee a good packing and may miss opportunities that require interlocking concave shapes. `scripts/benchmark_search.py` accepts `--counts` and `--areas` to compare explicit synthetic inventory distributions.

For insertion without local relaxation, the search caches the unchanged placed stones and uses an exact local precheck to reject impossible proposals before running the complete validator on a candidate it might accept. `use_prefilter=False` on `greedy_insert` provides the unfiltered reference path. The precheck is rebuilt after each accepted stone. With relaxation enabled, it bypasses relaxation for already-valid proposals but does not reject an invalid proposal that relaxation might repair.

`--strategy edge` alternates random positions with proposals that align sampled polygon edges on opposite sides of a prospective joint. This uses the actual outlines, including concave ones, but alignment is only a proposal: it can still intersect the anchor or other stones and must pass exact validation. Seeded durable insertion preserves the strategy.

For local rebuilding, `--patch-padding DISTANCE --patch-candidates N` restricts proposal centers to the removed stones' bounding region plus padding and limits how many unused stones are considered. The unused set mixes stones near the removed stones' sizes with smaller stones; removed stones remain eligible. Padding uses layout units. Optional relaxation can move stones after proposal, and exact whole-layout validation remains mandatory. These options apply to rebuild rounds; durable rebuild checkpoints retain them. `scripts/benchmark_patch.py` compares local and global rebuilds from identical starts under nominal equal post-insertion time budgets.

`--local-relaxation --relaxation-steps N` relaxes a nearby subset, then checks the entire layout; a failed global check causes insertion rollback. Neighborhood selection is heuristic and may miss interactions that arise during motion, so the full check is essential. Energy values returned by the neighborhood routine describe its subset. The option is checkpointed and remains experimental: short equal-time tests did not improve coverage over no relaxation.

`--max-relaxation-penalty N` optionally skips relaxation for candidates whose approximate overlap and outside-area penalty, divided by candidate stone area, exceeds `N`. Use it with `--relaxation-steps` and optionally `--local-relaxation`. This is a heuristic budget filter: it can skip candidates that a longer rearrangement might repair, and its buffer-based score does not certify clearance. Exact whole-layout validation still decides acceptance. Run metrics and durable checkpoints count relaxation attempts, successful valid outcomes, failures, and skipped candidates.

`--mobility-policy clearance` is an experimental alternative to the default bounding-circle rule for choosing which nearby stones can move during insertion relaxation. It uses exact initial polygon distances and a clearance-based neighborhood, while the local solver and final full-layout validation still check the resulting geometry. Checkpoints preserve the policy and count mobile-stone visits. In the short holdout comparison saved in `examples/benchmark_mobility_holdout.json`, this policy did not improve mean coverage, so the default remains unchanged.

For repeated insertion with stone-boundary checkpoints, use `--passes N` (the total pass target) and optionally `--max-seconds S` for the current invocation. Resume `iterative_checkpoint.json` with `--resume ... --passes N`; the saved strategy, RNG, margins, frozen stones, and current position in the pass are restored. The time limit is checked between stones, so a stone's remaining proposals and checkpoint write may overrun it. Fixed-pass replay is tested; wall-clock stop points vary by machine load. This mode uses scalar proposals and runs separately from pulse, rebuild, and exploration phases.

`--tolerance` sets the numerical distance-comparison slack in the same units as the layout (default `1e-9`). It is separate from physical clearances and uncertainty margins. A measured gap may be accepted down to the required gap minus this value; physical overlaps are still rejected, and the inward-buffer coverage check remains strict at the patio edge. Search, relaxation, batch checks, checkpoints, and placement manifests carry the selected tolerance. Resume uses the checkpoint's saved value; older checkpoints without it use the previous `1e-9` default.

Optional equal-coverage pocket ranking is enabled for rebuilds with `--secondary-resolution N --secondary-broad-distance D` and, optionally, `--secondary-edge-strip D`. The sampled interior area farther than the broad-distance threshold is minimized first; maximum sampled interior distance breaks ties. A higher covered area remains primary, and an equal-area move is accepted only when the sampled score improves. Distances use layout units and the grid is approximate. The settings and secondary-improvement count are checkpointed; evaluate sensitivity to grid resolution and do not treat the score as a joint-width or construction guarantee.

`uv run python scripts/benchmark_witness.py --size 12 --seed 42 --seconds 10 --output examples/known_fit_large` generates 144 synthetic stones with a validated complete placement, then runs checkpointed insertion from an empty layout. It saves the witness, empty input, result, plots, checkpoint and metrics. This provides a known-feasible recovery benchmark, but its nearly equal-sized quadrilaterals are simpler than measured flagstone. The budget is checked between stones and includes checkpoint writes; timed results depend on the machine and load.

`uv run python scripts/benchmark_witness_rebuild.py` applies checkpointed local rebuilds to the saved 60-second witness recovery run. It retains the insertion checkpoint's random state and writes a separate rebuild checkpoint and validated result; time is checked between rebuild rounds.

`uv run python scripts/benchmark_checkpoint_continuation.py` times a fixed number of insertion attempts from copies of a saved iterative checkpoint. It includes per-stone checkpoint writes and checks each resulting layout; use it for local profiling rather than as a cross-machine throughput claim. Checkpoint JSON is compact, while ordinary layout exports remain indented.

Rebuilding accepts the optional `--restore-removed` flag. After a patch is reinserted, it tries the original poses of removed stones that remain unused, keeping each only if the whole layout remains valid. Rebuild acceptance still requires an area improvement (or an enabled equal-area secondary improvement), and durable checkpoints retain the option. Short synthetic comparisons have not shown a packing improvement, so it is off by default. `scripts/benchmark_patch_size.py` compares patch sizes from one saved rebuild checkpoint under equal nominal per-run budgets; `--restore-removed` enables this fallback for the comparison.

The public relaxation, restart, and neighborhood-relaxation calls restore poses, active flags, and RNG state if an exception interrupts the call. Normal unsuccessful returns still report their violations as documented. The coordinate-descent step cutoff is relative to the square root of patio area; pass `step`, clearances, and tolerance in the layout's length units.

When an uncertainty model accompanies saved margins, the model is rechecked against those margins using relative numerical tolerance with no fixed absolute allowance. In particular, an explicitly nonzero bound cannot silently become zero when using small units.

Calibration reports include `control_coverage` for each source outline (and `patio_control_coverage` for a common-frame patio). It lists vertices outside the source control points' convex hull and the greatest distance to that hull in source units and in target units after applying the fitted scale. See `examples/calibration/control_coverage/extrapolation_report.json` for a synthetic case. This flags extrapolation; neither being inside the hull nor the reported distance bounds distortion or measurement error.

Stone IDs in layouts must be unique, nonempty strings. Numeric and blank IDs previously accepted by some paths are rejected because JSON object keys in margin and uncertainty maps are strings; convert those IDs and every related reference consistently before starting a new run. Integrity-protected checkpoints should be regenerated rather than edited by hand. Durable checkpoints preserve the state of NumPy's PCG64, PCG64DXSM, MT19937, Philox, and SFC64 generators; unsupported generators are rejected before a checkpoint is written.

The bounded exploration mode also accepts `--patch-padding` and `--patch-candidates`, with the same center-region and candidate-selection meaning as greedy rebuilding; its checkpoint retains these settings. Older exploration checkpoints without them retain unrestricted behavior. `uv run python scripts/benchmark_local_exploration.py` compares local greedy rebuilding with bounded exploration from the same detailed synthetic incumbent and saves each current layout, best layout, and checkpoint. Short runs have not shown a quality advantage.

`--strategy wall` mixes patio-boundary-aligned, stone-edge-aligned, and random insertion proposals. Boundary proposals include the requested edge clearance and uncertainty margins, but concavities and other stones can still invalidate them; full polygon validation remains mandatory. `uv run python -m flagstone --case search --seed 51 --strategy wall --proposals 5 --output examples/wall_proposals` creates an inspectable example. Short detailed-inventory comparisons have not established a general advantage over `edge`.

Exploration can optionally mix local rebuilds with individually validated stone movements: `--nudge-probability 0.5 --nudge-translation 0.01 --nudge-angle 0.1`. Translation is a per-axis bound in layout units; angle is in radians. A valid nudge is followed by insertion proposals using the exploration patch settings. Frozen stones remain fixed, invalid moves roll back, and the best valid incumbent and round-boundary checkpoint are retained. Zero probability (the default) preserves the earlier exploration schedule. The first short detailed-inventory comparison did not establish a packing benefit.

`inventory(..., vertex_profile='varied')` generates an additional synthetic mix: true four-edge squares and rectangles, a broad-notched state-like template, and detailed rounded outlines. It is a repeatable stress case, not measured stone geometry or a collection of actual state boundaries. `--vertex-profile varied` selects it in `scripts/benchmark_search.py`; `--detailed` retains its previous meaning. Passing `mixed=False` removes concavity in the varied profile.

`uv run python scripts/profile_continuation.py` profiles fixed checkpointed insertion work from the saved varied-inventory example and writes a CPU cProfile report. Its cumulative function times overlap and include profiler overhead; they are not GPU throughput or native-memory measurements.

Direct `Layout` construction requires stone outlines already centered at their area centroids; use `local_shape` and supply the corresponding centroid pose. Shapes whose centroids differ from the origin by more than 1e-12 of their extent on either axis are rejected. Version-1 JSON import accepts off-center outlines and adjusts the pose to preserve their world geometry, using the same scale-relative centering check. This tightens the direct Python API for previously accepted off-center shapes.

Repeated insertion validates the loaded layout once, validates each candidate before accepting it, and validates the final layout. Between stones it reuses the prior validity result because failed proposals restore poses and active flags. The ordinary `greedy_insert` API continues to validate both its input and output independently.

`validate_batch(..., max_batch_size=32)` limits CPU broad-phase working arrays to 32 candidates at a time by default. Set a smaller positive integer to reduce working memory or `None` to process the entire batch at once. Returned violation lists and the supplied input arrays still scale with total batch size. This is CPU chunking, not GPU acceleration; `scripts/benchmark_chunked_validation.py` measures Python-traced peak memory and verifies identical results.

The controller implementation has started with a bounded warm-start repair pilot in `scripts/corner_controller.py`. It evaluates every prefix, diagnoses which suffix to reopen, restarts from the best checked checkpoint, and requires saved-file verification before accepting an export. See [controller progress and usage](first_real_patio_controller_progress.md) for interfaces, validation, remaining work, and budget limitations. The historical corner search remains paused.

The first autonomous controller growth test from five stones finished at five: its best seven-stone attempt passed spacing but failed coverage with a 2.255598-inch certified upper bound. See the [experiment report](examples/controller_growth_from5_20261112/README.md) for the frozen policy, backtracking results, timings, and a repair-feedback defect discovered by the test.

A [second controller test with retained gap witnesses](examples/controller_growth_from5_20261112_v2/README.md) improved the best seven-stone upper bound to 2.162622 inches in 19.16 minutes, but still did not pass the two-inch gate. Matched starting groups and round-by-round comparisons are preserved in the report.
